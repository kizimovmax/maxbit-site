# MAXBIT — локальный запуск и редактирование (сборка 2.2; установка на хостинг — README_DEPLOY_WEBHOST1.md)

Состояние: локальная сборка, среда `local`, режим формы `LOCAL_TEST`. Сайт не опубликован. Домен, DNS, почта, CRM и аналитика не трогались.

## Что в проекте

| Путь | Назначение |
|---|---|
| `src/themes/maxbit/` | Собственная лёгкая тема (theme.json, шаблоны, паттерны, стили, SVG байт-в-байт) |
| `src/plugins/maxbit-core/` | Модуль содержания и форм: типы, поля, допуск, защита закрытых материалов, SEO, форма, адаптер доставки, события |
| `site/` | WordPress 7.1.2 (ядро) + `wp-config.php` без секретов + SQLite-плагин. Тема и модуль подключены симлинками в `site/wp-content/` |
| `scripts/` | `setup.sh`, `serve.sh`, `router.php`, `seed.php`, `reset-local.sh`, проверки `check*.sh`, `test-receiver.php`, `snapshots.sh`, `build-demo.py` |
| `docs/` | Бриф, тексты, приёмка, источники, ИИ-Практикум (из комплекта BUILD 2.0) |
| `reference/` | Эталонные SVG и снимки дизайна (из комплекта) |
| `reports/` | REVIEW_REPORT, OPEN_ITEMS, CURRENT_STATE, HTML-снимки страниц |
| `vendor/` | `wp-cli.phar`; скачанные архивы ядра/плагина (в Git не хранятся) |

`sources_private/` (полный исходник ИИ-Практикума) намеренно **не входит** в проект сайта — он остаётся в комплекте владельца.

## Требования

PHP ≥ 8.1 с расширениями `pdo_sqlite`, `sqlite3`, `mbstring`, `dom`, `gd`, `zip`. Для рабочего хостинга — MySQL/MariaDB (см. ниже). Node не нужен: сборки фронтенда нет.

## Запуск с нуля

```bash
# 1. Ядро (если папка site/ пуста — например, после клонирования без vendor/):
#    распакуйте WordPress 7.1.2 в site/ и SQLite-плагин в site/wp-content/plugins/sqlite-database-integration/
#    (в этой среде брались с GitHub: WordPress/WordPress тег 7.1.2; WordPress/sqlite-database-integration тег v3.0.2, сборка bin/build-sqlite-plugin-zip.sh)
# 2. Установка (соли пишутся в site/wp-config-local.php, пароль администратора — в logs/admin-password.local.txt):
bash scripts/setup.sh
# 3. Наполнение (идемпотентно; правки редактора не перезаписываются):
php vendor/wp-cli.phar --path=site --allow-root eval-file scripts/seed.php   # или wp maxbit seed, или кнопка «MAXBIT → Наполнение»
# 4. Сервер:
bash scripts/serve.sh          # http://localhost:8080  (порт: MAXBIT_PORT=8081)
```

Вход в панель: `http://localhost:8080/wp-login.php`, логин `maxbit_admin`, пароль из `logs/admin-password.local.txt`. Смените его при первом входе.


> **Важно (локальная разработка):** тема и модуль подключены в `site/wp-content` симлинками. Точку обновления (`/maxbit/v1/update/*`) на локальной копии не использовать — с 0.3.2 она сама отказывает при симлинке; для проверки установки копируйте тему в `site/wp-content/themes/maxbit` как обычную папку и возвращайте симлинк после.

Полный сброс локальной базы: `bash scripts/reset-local.sh` (удаляет и тестовые обращения).

```bash
bash scripts/check.sh            # 135: ресурсы через router, бренд, матрица доступа (5 состояний × каналы × роли), форма, безJS-чек, SEO по средам

bash scripts/check-fresh.sh      # 12: чистая установка во временный каталог + все наборы
```
Каждый набор пишет журнал в `reports/test-logs/` (дата, версии, ID синтетических записей). Синтетические записи помечены мета `_mb_test` и остаются в локальной базе; `reset-local.sh` их удаляет вместе с базой.
Локальные переопределения для проверок: `MAXBIT_ENV`, `MAXBIT_FORM_MODE`, `MAXBIT_DELIVERY_TEST_URL` читаются из переменных окружения **только** локальным `site/wp-config.php`; на хостинге — свой конфиг с константами.

**Браузерные проверки (вручную, нужен Chrome/Firefox):** `bash scripts/serve.sh` → http://localhost:8080 → DevTools → Device toolbar 390 и 1440 → проверить первый экран, меню, форму (успех/ошибка/повтор), клавиатуру, 200 %; Lighthouse — три прогона. Снимки сохранить в `reports/screenshots/`.

## Где что редактируется (без правки кода)

- **Страницы** (главная, Битрикс24, «Как работаем», «О компании», «Практика»): *Страницы*. Блоки редактора; секции главной — группы с классами `mb-section`, карточки — колонки с классом `mb-tiles`. Готовые паттерны — в списке паттернов, категория **MAXBIT**.
- **Решения**: *Решения*. Справа блок «Допуск к публичному показу» — отдельный флажок, ставит администратор. Без флага материал виден только авторизованным (даже при статусе «Опубликовано»).
- **Проекты**: *Проекты*. Поля «Структура кейса» (контекст → … → следующий шаг), поле «Учебный образец», внутренние поля (источники, разрешение, проверяющий) — никогда не выводятся.
- **Статьи**: *Записи*. Адрес `/praktika/{slug}/`.
- **SEO**: у любого материала блок «SEO и индексация»: title, description, флажок noindex. Canonical/robots/JSON-LD формируются автоматически.
- **Связи**: блок «Связанные материалы» (решение/статья/проект). Проект показывается только после допуска.
- **Контакты, среда стенда и состояние**: меню *MAXBIT*; наполнение — *MAXBIT → Наполнение*. Пустые контакты на сайте не показываются, вымышленные не подставляются.
- **Обращения**: меню *Обращения* — только администратор. Каждое помечено режимом `LOCAL_TEST` и статусом доставки.
- **Форма** на странице: паттерн «Форма обращения» или шорткод `[maxbit_form topic="…" heading="…" text="…" button="…"]`. Темы: `general`, `order_control`, `bitrix24`, `ai_practicum`, `article` (серверный белый список).

## Среды

`MAXBIT_ENV` в `wp-config.php`: `local` | `staging` | `production`.
- `local`/`staging`: `noindex,nofollow` для всех страниц, `robots.txt` — `Disallow: /`, sitemap выключен, жёлтая плашка среды, WP_HOME следует за хостом запроса (только для localhost).
- `production`: robots по флагам страниц, sitemap только допущенные и не-noindex, canonical от `home_url`.
Закрытые материалы закрыты во всех средах одинаково.

## Закрытые файлы клиентов
Файлы в `wp-content/uploads` отдаёт веб-сервер напрямую, независимо от допуска кейса. Модуль скрывает вложения закрытых материалов из REST и attachment-страниц, но не сам файл. Поэтому договоры, схемы и иные закрытые материалы в медиатеку не загружать (предупреждение в редакторе проекта). Полная защита — хранение вне webroot с выдачей через проверку прав — отдельная задача (OPEN_ITEMS).

## Как включить доставку в Битрикс24 (отдельное задание, не сейчас)

1. Согласовать входящий вебхук, карту полей, ответственного и уведомления.
2. В `wp-config.php` задать `MAXBIT_B24_WEBHOOK_URL` (секрет — только в конфиге на сервере, не в Git) и `MAXBIT_FORM_MODE` ≠ `LOCAL_TEST`.
3. Согласовать метод и контракт ответа (`MAXBIT_DELIVERY_PROTOCOL`, по умолчанию `bitrix24`: подтверждение — 2xx, JSON без `error`, `result` > 0 или массив с `ID` > 0). Подстановка произвольного вебхука без карты полей не даст рабочей интеграции.
4. Проверить на стенде: `_mb_delivery_status` → `delivered`; повторы до 3 попыток через WP-Cron, тайм-аут 5 с, одинаковый `request_id`; `delivered` терминален.
Статусы: `disabled` (адрес не задан), `pending`, `retry`, `delivered`, `failed`. «Принято сервером» ≠ «доставлено в CRM». `failed` пересматривается вручную (список обращений → колонка «Доставка»).

## Перенос на рабочий хостинг

- База: MySQL/MariaDB (удалить `site/wp-content/db.php`, задать `DB_*`). SQLite — только для локальной разработки.
- Секреты: соли и вебхук — в `wp-config-local.php` (права 600) или переменных окружения, никогда в репозитории. В не-local среде без солей сайт намеренно не стартует.
- За reverse proxy задать `MAXBIT_TRUSTED_PROXY` (IP прокси), иначе `X-Forwarded-For` игнорируется. Лимиты на уровне хостинга (fail2ban/WAF) — дополнительно к лимиту формы.
- Резервные копии, HTTPS, защита `/wp-admin/`, отдельные учётные записи — по разделу 3 в `docs/02_ACCEPTANCE.md`.
